# 1. ภาพรวมโครงการ (Project Overview)

## 1.1 ชื่อโครงการ

Smart Health & Emergency IoT Device

ระบบอุปกรณ์ IoT สำหรับติดตามข้อมูลสุขภาพ ตรวจสอบสถานะฉุกเฉิน และระบุตำแหน่งของผู้ใช้งานแบบ Real-Time ผ่านระบบ Web Dashboard

## 1.2 แนวคิดของโครงการ

โครงการนี้มีวัตถุประสงค์เพื่อพัฒนาอุปกรณ์ IoT ที่สามารถเก็บรวบรวมข้อมูลสุขภาพและข้อมูลสถานะของผู้ใช้งาน โดยนำข้อมูลจากเซนเซอร์และอุปกรณ์อิเล็กทรอนิกส์มาประมวลผลผ่านไมโครคอนโทรลเลอร์ ESP32

ข้อมูลที่ได้รับจะถูกส่งผ่านระบบสื่อสาร MQTT ไปยัง Backend Server ซึ่งพัฒนาด้วย Node.js และ Express จากนั้นจัดเก็บข้อมูลลงในฐานข้อมูล MySQL และนำมาแสดงผลบน Web Dashboard

ระบบจะรวบรวมข้อมูลสำคัญไว้ในหน้า Dashboard เดียว เพื่อให้ผู้ดูแลหรือผู้เกี่ยวข้องสามารถตรวจสอบสถานะของผู้ใช้งานได้สะดวกขึ้น

โครงการประกอบด้วย 3 ระบบหลัก ได้แก่

1. Health Monitoring – ระบบติดตามข้อมูลสุขภาพ
2. Emergency Monitoring – ระบบตรวจสอบสถานะฉุกเฉิน
3. Location Tracking – ระบบติดตามตำแหน่ง

## 1.3 วัตถุประสงค์

1. พัฒนาอุปกรณ์ IoT สำหรับตรวจสอบข้อมูลสุขภาพและสถานะฉุกเฉิน
2. พัฒนาระบบรับส่งข้อมูลระหว่างอุปกรณ์ IoT และ Web Application
3. พัฒนาระบบ Backend สำหรับประมวลผลและจัดเก็บข้อมูล
4. พัฒนาฐานข้อมูลสำหรับบันทึกข้อมูลสุขภาพและประวัติการแจ้งเตือน
5. พัฒนา Web Dashboard สำหรับแสดงข้อมูลแบบ Real-Time
6. ทดสอบการทำงานร่วมกันระหว่าง Hardware, Communication, Backend, Database และ Frontend

# 2. ขอบเขตของระบบ (Project Scope)

ระบบแบ่งออกเป็น 5 ส่วนหลัก

1. IoT Hardware
2. IoT Communication
3. Backend Server
4. Database
5. Frontend Web Dashboard

## 2.1 Health Monitoring

ระบบติดตามข้อมูลสุขภาพของผู้ใช้งาน โดยข้อมูลที่กำหนดไว้ในโครงการประกอบด้วย

- Heart Rate – อัตราการเต้นของหัวใจ
- Temperature – อุณหภูมิ
- SpO2 – ระดับออกซิเจนในเลือด

ข้อมูลเหล่านี้จะถูกส่งจากอุปกรณ์ IoT ไปยัง Backend เพื่อจัดเก็บและแสดงผลบน Dashboard

## 2.2 Emergency Monitoring

ระบบตรวจสอบสถานะฉุกเฉินของผู้ใช้งาน

ขอบเขตที่ต้องรองรับ ได้แก่

- แสดงสถานะปกติ
- แสดงสถานะฉุกเฉิน
- บันทึกประวัติเหตุการณ์ฉุกเฉิน
- แสดงเวลาที่เกิดเหตุการณ์
- แสดงข้อมูลผู้ใช้งานที่เกี่ยวข้อง
- เชื่อมโยงข้อมูลตำแหน่งกับเหตุการณ์ฉุกเฉิน

**หมายเหตุ:** วิธีตรวจจับเหตุฉุกเฉินจริง เช่น การกดปุ่ม SOS การตรวจจับการล้ม หรือการใช้เงื่อนไขจากเซนเซอร์ ยังต้องตรวจสอบและกำหนดให้ตรงกับ Hardware ที่ใช้งานจริง

## 2.3 Location Tracking

ระบบติดตามตำแหน่งของผู้ใช้งาน

ข้อมูลที่ระบบควรรองรับ ได้แก่

- Latitude
- Longitude
- ตำแหน่งล่าสุด
- เวลาที่ได้รับตำแหน่ง
- ประวัติตำแหน่ง (หากเปิดใช้การบันทึก)

ข้อมูลตำแหน่งสามารถนำไปแสดงบนแผนที่ภายใน Dashboard

ทั้งนี้ต้องตรวจสอบอุปกรณ์ GPS หรือแหล่งข้อมูลตำแหน่งจริงก่อนกำหนดรูปแบบการเชื่อมต่อ

## 2.4 Device Monitoring

ระบบติดตามสถานะอุปกรณ์ IoT

ข้อมูลประกอบด้วย

- Battery Level
- Device Status
- Connection Status
- Last Communication
- สถานะการเชื่อมต่อกับ Server

## 2.5 Web Dashboard

ระบบ Dashboard เป็นส่วนติดต่อผู้ใช้งานหลักของโครงการ

หน้าที่หลักคือรวบรวมข้อมูลจากอุปกรณ์ IoT และ Backend มาแสดงผลในรูปแบบที่เข้าใจง่าย

# 3. สถาปัตยกรรมระบบ (System Architecture)

โครงสร้างระบบที่กำหนดไว้ในโครงการมีดังนี้

Sensors → ESP32 → MQTT → Backend → MySQL → Web Dashboard

## 3.1 Hardware Layer

ประกอบด้วย

- ESP32
- Sensors
- อุปกรณ์ตรวจวัดข้อมูลสุขภาพ
- อุปกรณ์ที่เกี่ยวข้องกับการติดตามตำแหน่ง
- อุปกรณ์สำหรับตรวจสอบหรือแจ้งเตือนสถานะฉุกเฉิน

ESP32 ทำหน้าที่เป็นไมโครคอนโทรลเลอร์หลัก รับข้อมูลจากเซนเซอร์และเตรียมข้อมูลเพื่อส่งต่อไปยังระบบ Backend

## 3.2 Communication Layer

ใช้ MQTT เป็นโปรโตคอลหลักสำหรับรับส่งข้อมูลระหว่าง IoT Device กับ Backend

หน้าที่ของ MQTT ได้แก่

- รับข้อมูลจาก ESP32
- ส่งข้อมูลไปยัง Backend
- รองรับการสื่อสารแบบ Publish/Subscribe
- แยกช่องทางข้อมูลตามประเภทของอุปกรณ์หรือข้อมูล

ต้องกำหนด MQTT Broker, Port, Authentication และ Topic ให้ตรงกับระบบที่ใช้งานจริง

## 3.3 Backend Layer

เทคโนโลยีที่กำหนดไว้

- Node.js
- Express.js

หน้าที่ของ Backend

- รับข้อมูลจาก MQTT
- ตรวจสอบรูปแบบข้อมูล
- ประมวลผลข้อมูล
- จัดการข้อมูลผู้ใช้งานและอุปกรณ์
- บันทึกข้อมูลลง MySQL
- ให้บริการ API สำหรับ Frontend
- ส่งข้อมูลสถานะล่าสุดไปยัง Dashboard
- จัดการประวัติการแจ้งเตือนและเหตุการณ์ฉุกเฉิน

## 3.4 Database Layer

ใช้ MySQL เป็นระบบฐานข้อมูลหลัก

ข้อมูลที่ต้องจัดเก็บประกอบด้วย

- ข้อมูลผู้ใช้งาน
- ข้อมูลอุปกรณ์
- ข้อมูลสุขภาพ
- ข้อมูลตำแหน่ง
- สถานะอุปกรณ์
- ประวัติเหตุการณ์ฉุกเฉิน
- ประวัติการแจ้งเตือน

รายละเอียด Schema จริงต้องตรวจสอบจากฐานข้อมูลเดิมก่อนพัฒนาเพิ่มเติม

## 3.5 Frontend Layer

เทคโนโลยีที่กำหนดไว้

- React
- Vite
- Tailwind CSS

หน้าที่ของ Frontend

- แสดง Dashboard
- แสดงข้อมูลสุขภาพ
- แสดงสถานะอุปกรณ์
- แสดงสถานะฉุกเฉิน
- แสดงตำแหน่งผู้ใช้งาน
- แสดงข้อมูลย้อนหลัง
- ติดต่อ Backend API
- อัปเดตข้อมูลจากระบบ Real-Time

# 4. เทคโนโลยีที่ใช้ (Technology Stack)

| ส่วนประกอบ | เทคโนโลยี | หน้าที่ |
|---|---|---|
| Microcontroller | ESP32 | ควบคุมอุปกรณ์ IoT |
| Sensors | Health Sensors | เก็บข้อมูลสุขภาพ |
| Communication | MQTT | รับส่งข้อมูล |
| Backend | Node.js | ประมวลผล Server |
| Backend Framework | Express.js | จัดการ API |
| Database | MySQL | จัดเก็บข้อมูล |
| Frontend | React | สร้าง Web Application |
| Build Tool | Vite | พัฒนาและ Build Frontend |
| CSS Framework | Tailwind CSS | ออกแบบ UI |
| Map | ยังไม่กำหนด | แสดงตำแหน่งผู้ใช้งาน |

หมายเหตุ: รายการนี้เป็น Technology Stack ตามเอกสารโครงการ ไม่ใช่การยืนยันว่าแต่ละส่วนติดตั้งและเชื่อมต่อเสร็จสมบูรณ์แล้ว

# 5. การทำงานของระบบ (System Workflow)

ลำดับการทำงานหลักของระบบ

1. Sensors เก็บข้อมูลจากผู้ใช้งานหรือสภาพแวดล้อม
2. ESP32 รับข้อมูลจาก Sensors
3. ESP32 จัดเตรียมข้อมูลให้อยู่ในรูปแบบที่กำหนด
4. ESP32 ส่งข้อมูลผ่าน MQTT
5. Backend รับข้อมูลจาก MQTT
6. Backend ตรวจสอบและประมวลผลข้อมูล
7. Backend บันทึกข้อมูลลง MySQL
8. Frontend ติดต่อ Backend เพื่อดึงข้อมูล
9. Dashboard แสดงข้อมูลสุขภาพและสถานะอุปกรณ์
10. เมื่อมีเหตุการณ์ฉุกเฉิน ระบบต้องสามารถแสดงข้อมูลเหตุการณ์และข้อมูลตำแหน่งที่เกี่ยวข้องได้

Device Information

- Battery Level

Safety Information

- Emergency Status

# 6. ข้อกำหนดด้าน Frontend (Frontend Requirements)

Frontend ต้องเป็น Web Application ที่สามารถแสดงข้อมูลจาก Backend ได้อย่างถูกต้อง

## 6.1 Dashboard Overview

แสดงภาพรวมข้อมูลสำคัญ ได้แก่

- จำนวนอุปกรณ์ทั้งหมด
- จำนวนอุปกรณ์ออนไลน์
- จำนวนอุปกรณ์ออฟไลน์
- สถานะสุขภาพล่าสุด
- สถานะฉุกเฉิน
- ข้อมูลตำแหน่งล่าสุด

## 6.2 Health Monitoring Interface

แสดงข้อมูลสุขภาพในรูปแบบ Card และกราฟ

ข้อมูลประกอบด้วย

- Heart Rate
- Temperature
- SpO2

ควรมีข้อมูลเวลาที่ได้รับค่าล่าสุด และสามารถดูข้อมูลย้อนหลังได้

## 6.3 Emergency Interface

แสดงข้อมูลเหตุการณ์ฉุกเฉินอย่างชัดเจน

ควรรองรับ

- สถานะเหตุการณ์ปัจจุบัน
- เวลาที่เกิดเหตุการณ์
- ผู้ใช้งานที่เกี่ยวข้อง
- ตำแหน่งที่เกิดเหตุ
- ประวัติเหตุการณ์
- สถานะการจัดการเหตุการณ์

## 6.4 Location Interface

แสดงตำแหน่งบนแผนที่

ควรรองรับ

- ตำแหน่งล่าสุด
- Latitude
- Longitude
- เวลาอัปเดตตำแหน่ง

## 6.5 Device Interface

แสดงข้อมูลอุปกรณ์

- Device ID
- Device Name
- Battery Level
- Online/Offline
- Last Seen

## 6.6 User Interface

ออกแบบให้เข้าใจง่ายและเหมาะสำหรับการตรวจสอบข้อมูลอย่างรวดเร็ว

แนวทางการออกแบบ

- Responsive Design
- แสดงผลบน Desktop และ Mobile
- แยกหมวดหมู่ข้อมูลให้ชัดเจน
- ใช้สีแยกสถานะ
- มี Loading State
- มี Empty State
- มี Error State
- มีสถานะการเชื่อมต่อ
- หลีกเลี่ยงการแสดงข้อมูลจำลองแทนข้อมูลจริงโดยไม่ระบุ

**ข้อกำหนดสำคัญ:** ต้องตรวจสอบหน้า Dashboard ที่มีอยู่แล้วก่อน ห้ามสร้างหน้าใหม่ทับระบบเดิมโดยไม่จำเป็น

# 7. ข้อกำหนดด้าน Backend (Backend Requirements)

Backend เป็นตัวกลางระหว่าง IoT Device, MQTT, Database และ Frontend

## 7.1 MQTT Subscriber

ต้องสามารถ

- เชื่อมต่อ MQTT Broker
- Subscribe Topic ที่กำหนด
- รับข้อมูลจาก ESP32
- ตรวจสอบ Payload
- จัดการข้อมูลผิดรูปแบบ
- จัดการกรณี Broker หลุด
- Reconnect เมื่อการเชื่อมต่อขาดหาย
- บันทึกข้อมูลที่ผ่านการตรวจสอบ

## 7.2 REST API

Backend ต้องมี API สำหรับให้ Frontend เรียกใช้งาน

กลุ่ม API ที่ต้องรองรับในระดับข้อกำหนด

**Dashboard**
- ดึงข้อมูลภาพรวม
- ดึงสถานะระบบ
- ดึงข้อมูลล่าสุด

**Health**
- ดึงข้อมูลสุขภาพล่าสุด
- ดึงประวัติข้อมูลสุขภาพ

**Device**
- ดึงรายการอุปกรณ์
- ดึงรายละเอียดอุปกรณ์
- ดึงสถานะอุปกรณ์

**Emergency**
- ดึงสถานะฉุกเฉิน
- ดึงประวัติเหตุการณ์
- จัดการสถานะเหตุการณ์

**Location**
- ดึงตำแหน่งล่าสุด
- ดึงประวัติตำแหน่ง

ชื่อ Endpoint และ HTTP Method จริงต้องตรวจสอบจาก Backend ที่มีอยู่ก่อน ไม่ควรสร้างซ้ำโดยไม่จำเป็น

## 7.3 Real-Time Communication

ระบบควรรองรับการส่งข้อมูลจาก Backend ไปยัง Frontend เมื่อมีข้อมูลใหม่

สามารถใช้เทคโนโลยีที่เหมาะสม เช่น WebSocket หรือ Socket.IO ได้ หากยังไม่มีระบบนี้

ก่อนเพิ่มระบบใหม่ต้องตรวจสอบกลไกอัปเดตข้อมูลเดิมก่อน

## 7.4 Error Handling

ต้องรองรับ

- MQTT Connection Error
- Database Connection Error
- Invalid Payload
- API Error
- Device Offline
- Missing Data
- Timeout
- Server Error

Backend ต้องไม่หยุดทำงานทั้งหมดเพียงเพราะได้รับข้อมูลผิดรูปแบบจากอุปกรณ์หนึ่งตัว

- event_type
- message
- status
- created_at

**ข้อควรระวัง:** รายการด้านบนเป็นโครงสร้างข้อมูลที่เสนอเพื่อใช้เป็นแนวทางออกแบบเท่านั้น ไม่ใช่ Schema ที่ยืนยันว่ามีอยู่ในฐานข้อมูลปัจจุบัน AI ต้องตรวจสอบ Database จริงก่อนสร้างหรือแก้ไขตาราง

# 9. ระบบความปลอดภัย (Security Requirements)

ระบบควรมีการป้องกันข้อมูลและการเข้าถึงที่ไม่เหมาะสม

ข้อกำหนด

1. ไม่เก็บ Password เป็นข้อความธรรมดา
2. ใช้ Password Hashing
3. มีระบบ Authentication
4. มีระบบ Authorization ตามสิทธิ์ผู้ใช้งาน
5. ตรวจสอบข้อมูลก่อนบันทึก Database
6. ป้องกัน SQL Injection
7. ป้องกันการเข้าถึง API โดยไม่ได้รับอนุญาต
8. ไม่เปิดเผย MQTT Credentials
9. เก็บ Secret ไว้ใน Environment Variables
10. ใช้ HTTPS เมื่อ Deploy ระบบจริง
11. จำกัดการเข้าถึงข้อมูลสุขภาพและตำแหน่งตามสิทธิ์

ข้อมูลสุขภาพและตำแหน่งถือเป็นข้อมูลที่ต้องจัดการอย่างระมัดระวัง
